# Build Relay Protocol — v0

The wire protocol between a Build device (the bridge daemon) and a browser
client, mediated by the cloud relay. This document is **normative** for the
current wire: any change to the data shapes below is a wire change and
requires an amendment to this file. The corresponding handler implementations
in `build_bridge/e2ee.py`, `build_bridge/agent_server.py`, and
`build_bridge/complications.py` MUST match what is written here. Where the
spec and the code disagree today, the bug is in whichever one is wrong; this
file documents the contract, not "whatever the code happens to do."

This is a peer to the agent ↔ bridge protocol, which is defined in
`build_bridge/agent_protocol.py`. Where the agent protocol (BAP) has typed
envelopes, version negotiation, capability gating, and direction constraints,
the relay protocol today has none of those. Section 12 enumerates the known
gaps that follow-up RFCs will address.

### Changes since the initial v0 cut

- Payload shape validators landed (`build_bridge/relay_protocol.py`
  `VALIDATORS` registry). The dispatcher validates every incoming
  request payload before invoking the handler.
- Validation failures emit a structured error frame with a new
  `request_action` field (and any correlation tokens) — see §7. This
  is additive: the existing `{action: "error", error: "..."}` shape
  is preserved.
- §12 gap #4 (no payload validation) is now ADDRESSED for v0.

## 1. Status & versioning

- **Spec version**: v0 (no version field on the wire).
- **Wire version field**: not present today. Reserved for a future v1.
- **Stability**: normative for v0. A handler MUST NOT silently accept or
  emit a field absent from this spec; if a field is needed, amend this
  document in the same PR.
- **Backward compatibility**: there is no compatibility commitment for v0.
  v1 will introduce a versioned envelope (see §12).

---

## 2. Transport

The bridge maintains a single WebSocket connection to the relay
(`ws.py`). All browser traffic is multiplexed over that connection as
end-to-end encrypted (E2EE) frames; the relay never sees plaintext frame
contents.

- **Outer transport**: WebSocket, JSON-encoded messages.
- **Device→relay control channel**: signed Ed25519 handshake; defined
  separately in `ws.py` and `auth.py`. Out of scope for this document.
- **E2EE primitives**: X25519 ECDH for session key exchange; AES-GCM for
  frame encryption. Provided by the `build_secure_transport` library.
- **Session lifecycle**:
  - Browser → device: `session_init` — X25519-wrapped session key,
    signed by the browser's identity key.
  - Device → browser: `session_accept` — acknowledges and binds the
    session key.
  - Either side → other: `e2ee_envelope` — AES-GCM-encrypted data
    frames.
  - Either side: an inner frame with `frame_type: "close"` terminates
    the session.
- **Per-frame size limit**: 256 KB encrypted (relay-enforced). Handlers
  MUST self-trim large payloads — current trim budgets live alongside
  the handlers (e.g. `_MAX_ACTIVITY_TOOL_USES = 50`, `_MAX_FILE_READ =
  100_000`, `_MAX_URL_FETCH = 500_000` chunked, `_MAX_DIR_ENTRIES =
  1000`, `_MAX_DIFF_SIZE = 100_000`).

## 3. Frame format

### 3.1 Outer WebSocket message

```jsonc
{
  "type": "session_init" | "session_accept" | "e2ee_envelope",
  "session_id": "<uuid>",
  "session_init":  /* present iff type == "session_init"  */ { ... },
  "envelope":      /* present iff type == "e2ee_envelope"  */ "<base64 ciphertext>"
}
```

Other `type` values are not part of this protocol and MUST be ignored by
the receiver.

### 3.2 Inner decrypted frame

After `decrypt_envelope`, the inner frame is:

```jsonc
{
  "frame_type": "data" | "close",
  "sender":     "client" | "device",
  "route_to":   "client" | "device",
  "message_id": "<uuid>",      // OPTIONAL; rarely echoed in responses today
  "payload":    { "action": "<name>", ... }
}
```

- `frame_type: "close"` carries no payload and terminates the session.
- `frame_type: "data"` carries an application-level payload routed by
  `payload.action`.
- `sender` identifies the originator of the frame ("client" = browser,
  "device" = bridge).
- `message_id` is generated by the originator. It is reserved as a
  request/response correlation token but is **not echoed by most
  device-side handlers today**. See §12.

### 3.3 Routing key

`payload.action` (string) is the routing key for the data plane. Action
names are case-sensitive. There is no namespace prefix on the wire today;
namespaces in this spec are organizational only.

## 4. Request / response / broadcast model

The relay protocol supports three message patterns over the same
session:

- **Request → response** (browser-initiated): the browser sends a frame
  with one action name; the device replies with one (sometimes more)
  frames, each carrying a different action name (e.g. `list_channels`
  → `channel_list`). Most actions follow this pattern.
- **Streaming response** (browser-initiated): one request, many
  response frames terminated by `done: true`. Used by
  `terminal_exec`, `file_read` (image chunking), and `files_list` (a
  fast bare listing followed by a git-enriched listing).
- **Broadcast** (device-initiated, unsolicited): the device pushes a
  frame to **all** active browser sessions on a channel. Used for
  agent events, system messages, message echoes, and complications.

### 4.1 Correlation

There is no universal correlation between a request and its response.
The following per-action correlation tokens exist today and MUST be
echoed by their respective response frames:

| Token         | Set by   | Echoed by                                    |
|---------------|----------|----------------------------------------------|
| `command_id`  | browser  | `terminal_output` frames (streaming + final) |
| `file_id`     | browser  | `chunk_ack`, `upload_accepted`, `upload_error` |
| `request_id`  | browser  | `url_fetch_result`                           |
| `message_id`  | browser  | `delivered`, `delivery_failed`               |

For every other action there is no echo, so the browser correlates by
action name and channel_id. This is a known gap (see §12).

### 4.2 Broadcast vs response

A response frame is sent only to the originating session via
`_send_frame`. A broadcast frame is sent to every active session for the
channel via `broadcast_to_sessions`. The browser deduplicates by message
ID where applicable (e.g. the originating tab sees both a `delivered`
response and a `message` broadcast for its own send; the message ID
distinguishes the source).

## 5. Browser → device actions

Each action below specifies request payload, response payload(s), and
side effects. All actions take a frame whose `payload.action` matches
the action name and whose other payload fields are documented inline.

Field type notation:
- `string`, `int`, `float`, `bool` are JSON primitives.
- `<type>?` means optional.
- `<default>` after a field name means the default if the field is
  absent.

### 5.1 Channels

#### `list_channels`

Request payload:
```jsonc
{ "action": "list_channels" }
```

Response — one `channel_list` frame, **followed by zero or more
`complication:update` frames** seeded from the current complication
registry:

```jsonc
{
  "action": "channel_list",
  "channels": [
    {
      "id": "<uuid>",
      "name": "<string>",
      "created_at": <float seconds since epoch>,   // from MessageStore
      // Enriched fields (present iff an agent_channels row exists):
      "harness": "<string>",
      "model": "<string>",
      "agent_name": "<string>",        // harness display name, e.g. "Claude Code"
      "working_directory": "<string>",
      "effort": "<string>",
      "plan_mode": true | false,
      "auto_approve_tools": true | false,
      "last_seen_at": "<iso8601 string or null>",  // from AgentStore
      "is_running": true | false       // worker alive AND channel status == "active"
    }
  ],
  "agent_cwd": "<absolute path>"        // os.getcwd() at evaluation time
}
```

Side effects: reads `MessageStore.list_channels()` and
`AgentStore.get_channel()`; consults `AgentSpawner.is_running()` for
the live `is_running` bit.

Source: `e2ee.py:310`.

#### `create_channel`

Request:
```jsonc
{
  "action": "create_channel",
  "name": "<string>",                 // required, trimmed
  "harness": "<string>?",
  "model": "<string>?",               // defaults to harness.default_model if harness given
  "effort": "<string>?",
  "system_prompt": "<string>?",
  "working_directory": "<string>?",
  "auto_approve_tools": false         // bool, default false
}
```

Response — one `channel_created` frame:
```jsonc
{
  "action": "channel_created",
  "channel": { "id": "<uuid>", "name": "<string>", "created_at": <float seconds since epoch> },
  // Present iff harness was provided and spawn succeeded:
  "agent": { "agent_id": "<string>", "harness": "<string>", "model": "<string>", "pid": <int> },
  // Present iff harness was provided and spawn failed:
  "agent_error": "<string>"
}
```

Error response (empty `name`):
```jsonc
{ "action": "error", "error": "channel name required" }
```

Side effects: inserts row in `MessageStore`; ensures `agent_channels`
stub row exists; optionally invokes `AgentSpawner.spawn()`.

Source: `e2ee.py:359`.

```jsonc
{ "action": "rename_channel", "channel_id": "<uuid>", "name": "<string>" }
```

Response:
```jsonc
{ "action": "channel_renamed", "channel_id": "<uuid>", "name": "<string>" }
```

```jsonc

```

Side effects: `MessageStore.rename_channel()`.

Source: `e2ee.py:437`.

#### `update_channel`

Request:
```jsonc
{
  "action": "update_channel",
  "channel_id": "<uuid>",                   // required
  "working_directory": "<string>?",
  "model": "<string>?",
  "effort": "<string>?",
  "harness": "<string>?",
  "auto_approve_tools": <bool>?
}
```

Any of the optional fields, if present, is applied. `working_directory:
null` is treated as "no change" because the handler keys on `is not
None`; sending an empty string applies the empty string.

Response — one `channel_updated` frame that echoes the request's
optional fields (potentially `null`):
```jsonc
{
  "action": "channel_updated",
  "channel_id": "<uuid>",
  "working_directory": <echo>,
  "model": <echo>,
  "effort": <echo>,
  "harness": <echo>,
  "auto_approve_tools": <echo>
}
```

Followed by zero or one `system_message` broadcast summarising what
changed (e.g. `"Harness → claude-code · Model → claude-opus-4.7"`).

Followed (out-of-band, asynchronous) by an agent restart **iff**
`harness` or `auto_approve_tools` changed — these settings are read
once at spawn time.

Error (missing `channel_id`):
```jsonc
{ "action": "error", "error": "channel_id required" }
```

Side effects: updates `AgentStore` columns; may call
`AgentSpawner.restart()`; broadcasts a `system_message`.

Source: `e2ee.py:464`.

#### `delete_channel`

Request:
```jsonc
{ "action": "delete_channel", "channel_id": "<uuid>" }
```

Response:
```jsonc
{ "action": "channel_deleted", "channel_id": "<uuid>" }
```

Error (missing `channel_id`):
```jsonc
{ "action": "error", "error": "channel_id required" }
```

### 5.2 Messages

#### `get_messages`

Request:
```jsonc
{
  "action": "get_messages",
  "channel_id": "<uuid>",
  "limit": 50,                  // int, default 50
  "before": <float seconds since epoch>?   // pagination cursor (returns messages older than)
}
```

Response — one `messages` frame containing E2EE messages and AgentStore
chat messages merged chronologically (deduplicated by message id),
clipped to the most recent `limit` entries:

```jsonc
{
  "action": "messages",
  "channel_id": "<uuid>",
  "messages": [
    {
      "id": "<uuid>",
      "channel_id": "<uuid>",
      "sender": "client" | "<agent display name>",  // e.g. "Claude Code"
      "content": "<string>",
      "created_at": <float seconds since epoch>,
      "delivered_at": <float>,
      "read_at": <float>,
      "attachments": [...]?,    // E2EE messages only
      "metadata": "<JSON string>"?,        // AgentStore messages only; raw JSON-encoded string (not parsed)
      "suggested_actions": ["<string>"]?   // AgentStore messages only; parsed array of action labels
    }
  ]
}
```

Side effects: read-only from both stores.

Source: `e2ee.py:604`.

#### `message`

Sends a chat message from the user to the channel's agent.

Request:
```jsonc
{
  "action": "message",
  "channel_id": "<uuid>",
  "content": "<string>",        // required UNLESS attachments are present
  "plan_mode": <bool>?,
  "model": "<string>?",         // per-message override
  "effort": "<string>?",        // per-message override
  "attachments": [              // optional
    { "file_id": "<uuid>", "filename": "<string>", "size": <int>, "mime_type": "<string>" }
  ]
}
```

The request frame's outer `message_id` field is the user message's
identity and MUST be set; it is the value echoed in `delivered`,
broadcast in the `message` echo, and forwarded to the agent.

Response — one sync `delivered` frame:
```jsonc
{ "action": "delivered", "message_id": "<uuid>", "channel_id": "<uuid>" }
```

Broadcast — one `message` frame to all sessions on the channel (the
originating tab dedupes by `message.id`):
```jsonc
{
  "action": "message",
  "message": {
    "id": "<uuid>",
    "channel_id": "<uuid>",
    "sender": "client",
    "content": "<string>",
    "created_at": <float>,
    "attachments": [...]?
  }
}
```

If the agent is down, the device attempts an auto-restart and emits an
ephemeral `system_message` broadcast (`"Agent is restarting, please
standby..."`). If the agent cannot be reached, a `delivery_failed`
frame is sent:
```jsonc
{ "action": "delivery_failed", "message_id": "<uuid>", "channel_id": "<uuid>" }
```

Side effects: stores the message in `MessageStore`; marks delivered;
broadcasts the message; forwards to the agent via BAP `chat.message`,
enriching attachment paths with the upload final-dir; persists
`plan_mode`/`model`/`effort` overrides to `AgentStore` when provided;
may restart the agent.

Source: `e2ee.py:844`.

#### `retry_message`

Re-runs the delivery flow for a previously failed message.

Request:
```jsonc
{ "action": "retry_message", "channel_id": "<uuid>", "message_id": "<uuid>" }
```

Response: identical to `message` (delegates to the chat-message handler
with a synthetic frame). If the original message is not found in the
store, replies with `delivery_failed`.

Source: `e2ee.py:1005`.

#### `mark_read`

Request:
```jsonc
{ "action": "mark_read", "channel_id": "<uuid>", "message_ids": ["<uuid>", ...] }
```

Response (only when `message_ids` is non-empty):
```jsonc

```

Side effects: `MessageStore.mark_read()` per id.

Source: `e2ee.py:1090`.

#### `mark_seen`

Fire-and-forget. Marks the channel as visually seen by the user (used
for unread-count badging).

Request:
```jsonc
{ "action": "mark_seen", "channel_id": "<uuid>" }
```

Response: **none**. Silent on success and on failure.

Side effects: `AgentStore.mark_channel_seen()`.

Source: `e2ee.py:1406`.

### 5.3 Activity

#### `get_activity`

Request:
```jsonc
{ "action": "get_activity", "channel_id": "<uuid>" }
```

Response — one `activity_history` frame trimmed to the last
`_MAX_ACTIVITY_TOOL_USES` (50) tool uses plus their matching tool
results plus reasoning text entries:

```jsonc
{
  "action": "activity_history",
  "channel_id": "<uuid>",
  "entries": [
    { "type": "tool_use" | "tool_result" | "text", "data": {...}, "created_at": "<iso8601>" }
  ]
}
```

`data` shapes:
- `tool_use.data`: `{ id, name, input }` — string values in `input`
  truncated to 200 chars with `…`.
- `tool_result.data`: `{ tool_use_id, content, is_error }` —
  `content` truncated to 1000 chars with `…`.
- `text.data`: `{ content }` — truncated to 1000 chars with `…`.

If the serialized payload still estimates > 200 KB encrypted, the
handler halves entries until it fits.

Side effects: read-only from `AgentStore.get_activity_history()`.

Source: `e2ee.py:704`.

### 5.5 Interactions

#### `interaction_response`

Forwards the user's answer to a BAP `interaction.request` back to the
agent. Fire-and-forget at the relay layer; failures surface as an
inline error message frame.

Request:
```jsonc
{
  "action": "interaction_response",
  "channel_id": "<uuid>",            // required
  "interaction_id": "<uuid>",        // required
  "selected_option": "<string>?",     // single-choice answer
  "freeform_response": "<string>?",   // free text answer
  "selected_options": ["<string>"]?, // multi-select answer
  "step_answers": { ... }?           // for multi-step / form interactions
}
```

Response on the happy path: **none**.

Response on agent send failure: a `message` frame with an error
notice (see §5.2 broadcast format) and `content: "⚠ Failed to send
response to agent. The agent may have disconnected."`. The error
message is also persisted to `MessageStore` so it appears in scrollback.

Side effects: `AgentStore.resolve_interaction()`;
`AgentServer.send_interaction_response()` over the BAP wire.

Source: `e2ee.py:1440`.

### 5.8 Terminal

#### `terminal_exec`

Streaming. Runs a shell command in the channel's working directory and
streams stdout/stderr back as `terminal_output` frames. The handler
runs as a background task so other actions (notably `terminal_kill`)
can interrupt it on the same session.

Request:
```jsonc
{
  "action": "terminal_exec",
  "channel_id": "<uuid>",            // required
  "command": "<string>",             // required, trimmed; empty is ignored
  "command_id": "<uuid>?",           // echoed in every response frame
  "cwd": "<absolute or ~ path>?"     // defaults to channel.working_directory else os.getcwd()
}
```

Streaming response — zero or more interim frames, batched every 100 ms
or 16 KB:
```jsonc
{
  "action": "terminal_output",
  "channel_id": "<uuid>",
  "command_id": "<uuid>?",           // present iff request had one
  "data": "<utf-8 chunk>",
  "done": false
}
```

Final response — exactly one frame:
```jsonc
{
  "action": "terminal_output",
  "channel_id": "<uuid>",
  "command_id": "<uuid>?",
  "done": true,
  "exit_code": <int>,
  "cwd": "<resulting absolute path>" // captured via a sentinel in the wrapped command
}
```

If the spawn fails outright the single frame carries
`data: "Failed to execute: ..."`, `done: true`, `exit_code: 1`, and

the device can recover the resulting working directory after `cd`
operations.

Source: `e2ee.py:2430`.

## 7. Errors

The relay protocol does not have a uniform error envelope. The shapes
currently in use are:

1. **Generic action error** — emitted by the centralized dispatcher
   when a payload validator rejects the frame:
   ```jsonc
   {
     "action": "error",
     "error": "<message>",                  // e.g. "missing required field: channel_id"
     "request_action": "<original-action>", // e.g. "rename_channel"
     // Plus any correlation tokens that were present in the request:
     "channel_id"?: "<uuid>",
     "command_id"?: "<uuid>",
     "file_id"?: "<uuid>",
     "request_id"?: "<uuid>",
     "message_id"?: "<uuid>"
   }
   ```
   `request_action` is always present on dispatcher-emitted errors;
   the correlation tokens are echoed only when the original request
   carried them as strings. Older browsers can safely ignore
   `request_action` — the shape is otherwise unchanged from the
   pre-validator handler-emitted error frames.

   Handler-internal validation errors (e.g. path-escape inside
   `file_read`, "agent not available" inside `reset_session`) emit the
   same `{action: "error", error: "..."}` skeleton but without
   `request_action` (those are not dispatcher-routed). When in doubt,
   the browser should branch on `action == "error"` first and use
   `request_action` if present for routing.

2. **Action-specific result with `error` field**: where the action
   normally returns a result frame, the error is folded into the same
   result frame with an `error` string. Used by:
   `files_list_result`, `files_commits_result`, `file_read_result`,
   `file_diff_result`, `url_fetch_result`.

3. **Upload-specific error**:
   `{ "action": "upload_error", "file_id": "<uuid>", "error": "<message>" }`
   (plus optional `path` for the "file exists" case).

4. **Delivery failed**:
   `{ "action": "delivery_failed", "channel_id": "<uuid>", "message_id": "<uuid>" }`

5. **Silent failure**: a few actions log the error server-side and
   send nothing back. Notably:
   - `mark_seen` (any failure swallowed).
   - `interaction_response` (only sends an error if the agent-side
     forward fails; persistence errors are silent).
   - `complication:action` (delegates to the manager; relay returns
     nothing).
   - `retry_message` when the original message isn't found is
     reported via `delivery_failed`, not a generic error.

This inconsistency across shapes #1–#5 is tracked in §12 as a v1
candidate (single normalised `validation_error` action).

## 10. Inner-frame `frame_type: "close"`

Either side may send a frame with `frame_type: "close"`. The receiver
MUST remove the session from its session map and stop sending further
frames on that `session_id`. No payload is required.

Source: `e2ee.py:219`.

## 11. Side-effect summary

A non-exhaustive map of which stores and subprocesses each action
touches. Useful for the refactor (§12): handlers should converge on a
narrow set of injected dependencies rather than the current pattern of
reaching through `self._agent_server` to grab whichever store they
need.

| Surface              | Stores touched                                  | Subprocesses                    |
|----------------------|-------------------------------------------------|---------------------------------|
| Channels             | `MessageStore`, `AgentStore`                    | `AgentSpawner.spawn/stop/restart` |
| Messages             | `MessageStore`, `AgentStore`                    | —                               |
| Activity             | `AgentStore` (read)                              | —                               |
| Agents               | `AgentStore`                                     | `AgentSpawner.*`                |
| Interactions         | `AgentStore`                                     | —                               |
| Sessions             | `AgentStore`                                     | `AgentSpawner.restart`          |
| Complications        | `AgentStore`                                     | `git` (via `_run_git`)          |
| Terminal             | —                                                | `bash -c <wrapped command>`     |
| Files                | —                                                | `git status` / `git diff` / `git check-ignore` / `git log` / `git ls-files` |
| URL                  | per-tab cookie jar (in-memory)                   | —                               |
| Uploads              | filesystem at `~/.config/build/uploads`          | —                               |

## 12. Known gaps (v1 candidates)

These are wire-level issues that v0 documents but does not fix.
Each is a candidate for its own follow-up RFC; this section is the
backlog.

1. **No envelope version field.** Compare to BAP's `v: 1`. A
   versioned inner frame is required before any breaking change can be
   rolled out alongside older clients.
2. **No universal request/response correlation.** `message_id` exists
   in the frame schema but is rarely echoed by device handlers.
   Per-action tokens (`command_id`, `file_id`, `request_id`) cover
   their own actions but leave the rest correlated only by action name
   + channel_id.
3. **Inconsistent action naming**:
   - Request/response stems don't match (`list_channels` →
     `channel_list`, `get_messages` → `messages`, `list_harnesses` →
     `harness_list`, `list_workers` → `worker_list`).
   - Mixed snake_case and colon-namespaced
     (`complication:action`, `complication:update`,
     `complication:remove`) without a documented rule.
   - The `cancel` action's response is `cancel_ack`, but
     `stop_agent`'s response is `agent_stopped` — different verb
     framings for related operations.
4. **No payload schema validation at dispatch.** ~~Handlers each call
   `payload.get("field", default)`; absent or wrong-typed fields are
   silently coerced.~~ **(ADDRESSED)** As of the validators PR,
   `relay_protocol.py` ships a `VALIDATORS` registry with one
   `validate_<action>` function per dispatched action; the dispatcher
   in `E2EESession._handle_data_frame` invokes the validator before
   the handler and emits a structured error frame on failure (see
   §7 shape #1). Handlers no longer carry redundant "required field"
   checks. A v1 follow-up may introduce a dedicated `validation_error`
   action name distinct from the generic `error` shape.
5. **Inconsistent error envelopes** (see §7). A single error envelope
   shape with a stable error code (`{action: "error", code, message,
   request_action?, channel_id?}`) would let the browser handle
   errors uniformly.
6. **Dispatch is a 60-line `elif` chain in `e2ee.py:227-308`.** No
   registry of action → handler; no way to introspect what actions
   are supported. The refactor should introduce a dispatch table that
   can be enumerated.
7. **Storage leaks across the dispatcher.** Handlers reach through
   `self._agent_server` to mutate `AgentStore` and `MessageStore`
   directly. The dispatch layer should not import storage; storage
   mutations should be callbacks behind injected interfaces.
8. **Some actions are fire-and-forget by accident, not by design.**
   `mark_seen`, `complication:action`, and `interaction_response`
   return nothing on success, with only logging on failure. The
   browser has no way to confirm or recover.
9. **`complication:update.timestamp` duplicates `changed_at`.** Kept
   for back-compat in some clients; v1 should pick one.
10. **Image `file_read` chunking is unspecified beyond shape.** Frames
    are not ordered by relay; the browser is expected to reassemble
    by `chunk_index` but there is no termination signal beyond
    `chunk_index == chunk_total - 1`.
11. **`url_fetch` has no allowlist enforced at the protocol layer.**
    The handler accepts any URL httpx can resolve. Localhost-only
    enforcement, if intended, should be normative.
12. **Mixed parsing of stored JSON in `messages` responses.**
    `metadata` on AgentStore chat messages goes over the wire as a
    raw JSON-encoded string while `suggested_actions` is parsed before
    sending. Both should be parsed JSON arrays/objects in v1.
13. **`created_at` types differ across stores.** `MessageStore`
    returns float seconds; `AgentStore` returns ISO 8601 strings.
    `get_messages` normalizes by converting AgentStore values to
    floats, but `channel_list` exposes both (float for `created_at`
    on the base entry, ISO 8601 for `last_seen_at` from the enriched
    fields). v1 should standardize on one format end-to-end.
14. **`message` response interleaves `delivered` and
    `delivery_failed`.** A `delivered` frame is always sent the
    moment the message hits the device store, BEFORE any attempt to
    forward to the agent. If the agent forward subsequently fails, a
    `delivery_failed` frame follows. A client that treats `delivered`
    as terminal will believe the message reached the agent when it
    didn't. v1 should split into a "stored" ack and an end-to-end
    "delivered to agent" ack with separate names.

A v1 envelope might look like:

```jsonc
{
  "v": 1,
  "id": "<uuid>",                    // correlation id, always echoed
  "ref": "<uuid>?",                  // response refers to a prior request id
  "frame_type": "data" | "close",
  "sender": "client" | "device",
  "route_to": "client" | "device",
  "type": "<namespace>.<action>",    // single stable name; no request/response divergence
  "payload": { ... },
  "error": null | { "code", "message", "details"? }
}
```

— mirroring `agent_protocol.py`'s envelope discipline. Specifying v1
is out of scope for this document.

## 13. Out of scope

- The relay's own internals (routing, presence, fanout): the relay
  treats every frame as opaque after envelope inspection.
- The device → relay control plane (signed handshake, transport key
  upload, heartbeat): see `ws.py` and `auth.py`.
- The agent → bridge protocol (BAP): see `agent_protocol.py` and its
  consumers `agent_server.py`/`agent_wrapper.py`.
- The browser-side implementation. The browser MUST behave as if this
  spec is the contract, but its codebase is in a separate repo.
